# Review Report — PRD Adversarial (Module M2: Academic GPU Policy Engine)

**Lens:** bmad-review-adversarial-general (cynical / assumption / specificity / internal-consistency / claim-vs-evidence / incentive attacks)
**Target:** `planning/prd.md` (status: FINAL, post-adversarial-triage)
**Upstream contracts checked against:** `SPEC.md` (CAP-1, CAP-2, CAP-3, CAP-6, CAP-7, CAP-8, CAP-10, Constraints), `ARCHITECTURE-SPINE.md` (AD-1, AD-4, AD-5, AD-6, AD-10, AD-11, rules 1, 2, 4, 5, 6, 7, 8)
**Course brief:** not parseable in this session (PDF input unsupported); SPEC + spine treated as the binding contract
**Reviewer posture:** assumed the author is overconfident and under-tested; every "100%", "zero", "strict", "total", and "immutable" in the document was treated as a claim to be falsified, not as a guarantee

**Findings:** 28 total — 8 Critical, 14 High, 5 Medium, 1 Low

**Verdict:** Not ready for an architecture phase. This is a well-presented document with a genuinely good conceptual spine (the three-outcome vocabulary, the "fail-closed" instinct, the named-persona discipline, the append-only pin) but it fails on the two things a PRD exists to guarantee: that every rule has a defined, reachable outcome, and that every claim is checkable. Concretely: **the entire rule catalogue contains zero `ALLOW` rows and no default**, so the module's most common outcome is unproducible and FR-1's headline "exactly one terminal outcome" is unfalsifiable; **four of the fourteen rules are unreachable, shadowed, or unsatisfiable** (`R-TIER-03` is shadowed by `R-TIER-02` under a strict total order, `R-STRADDLE-01` requires an `ALLOW` that cannot exist, `R-GRACE-01` swallows `R-STRADDLE-01`'s entire population, and `R-FRZ-02` sits at precedence 14 where five earlier `DENY`s make FR-2's "100% admitted" arithmetically impossible); **FR-10 and NFR-12 flatly contradict each other** on the same stale model-catalog read; and **the module owns a freeze console, a freeze state machine, and a freeze-persona SLA, but defines zero write interface and never assigns an owner to the `FreezeState` aggregate** — a direct rule-1 violation that also breaks the PRD's own RISKY-assumption fallback. Two further defects are not merely untidy but unsafe: `exam_binding` is an unvalidated client-supplied M4 reservation id that is the *sole* exemption from the freeze, night, and lab rules, and `R-QUOTA-02` grants a cap computed from a 5-second-stale read balance, which is precisely the read-then-write pattern spine rule 4 calls "an invariant violation, not a future optimization." An architecture phase handed this document would have to re-derive the rule precedence, invent the freeze-write boundary, and pick one side of the FR-10/NFR-12 conflict — none of which is architecture's job. Recommended: run one triage pass fixing Criticals 1–8 and Highs 9–14 (all are contained, mostly a table rewrite plus a new freeze port), then re-review before any story breakdown.

### PRD-1 — There is no `ALLOW` rule and no default: the module's most common outcome cannot be produced

- **Severity:** Critical
- **Location:** §6.2 (all 14 rows) / §6.1 step 4 / FR-1 / NFR-6
- **Attacked text:** §6.1 step 4: "4. REDUCE        first rule with a terminal outcome becomes primary_rule_id; remaining matched rules are kept" — and FR-1: "100% of requests in the FR test matrix resolve to exactly one of `ALLOW`/`DENY`/`CONSTRAIN`. Zero requests produce an empty or multi-valued outcome."
- **Attack:** I read all fourteen rows of §6.2. Outcomes present: `DENY` (R-FRZ-01, R-TIER-01, R-TIER-02, R-AUTH-01, R-AUTH-02, R-LAB-01, R-NIGHT-01, R-QUOTA-01) and `CONSTRAIN` (R-TIER-03, R-GRACE-01, R-STRADDLE-01, R-QUOTA-02, R-CONTEND-01, R-FRZ-02). **`ALLOW` appears nowhere as an outcome.** A well-formed request — an enrolled student asking for 1×24 GB at 14:00 with quota remaining, no freeze, no class window, nothing cordoned — matches no rule, so step 4 finds no terminal outcome. There is no `else`/default row, no `R-ALLOW-01`, and no defined behaviour for the all-`NO_MATCH` case. The `Decision` type has no representation for "no rule fired" (`primary_rule_id` is a non-nullable field, §3.1/§5). This breaks three separate claims simultaneously: FR-1's "exactly one terminal outcome" (the true outcome is *zero*), NFR-6's "100% of decisions carry `primary_rule_id`", and §1's "returns exactly one of `ALLOW`, `DENY`, or `CONSTRAIN`, always with a named rule". §10 has no NP entry for it either — NP-8 only covers duplicate precedence weights. It also makes FR-3's "Zero cases substitute a 24 GB node for a 48 GB requirement" vacuous (§3.1 NG-1 says the engine returns class-level feasibility and never places, so it structurally cannot substitute).
- **Proposed fix:** Add row 15 to §6.2: `` | 15 | `R-ALLOW-01` | No rule at positions 1–14 produced a terminal outcome | `ALLOW` | `POL-DEFAULT` | ``, and add a step 4b to §6.1: "if no rule produced a terminal outcome, the reduction resolves to `ALLOW` with `primary_rule_id = R-ALLOW-01` and an empty `constraints[]`". Amend NFR-6 to "100% of decisions carry a `primary_rule_id` ∈ the rule registry". Add NP-9 covering the all-`NO_MATCH` case explicitly.
- **Confidence:** High

### PRD-2 — Strict total precedence makes `R-TIER-03` unreachable, which makes FR-3's acceptance condition self-cancelling

- **Severity:** Critical
- **Location:** §6.2 rows 3 and 4 / FR-3
- **Attacked text:** Row 3: "`R-TIER-02` | The request is physically feasible **fleet-wide**, but no class available to the actor's clearance satisfies it (e.g. 48 GB requested, actor capped at 24 GB) | `DENY`". Row 4: "`R-TIER-03` | The request exceeds the actor's clearance (`max_gpu_count` / `max_vram_gb`) but the model has a catalog variant satisfying the actor's cap | `CONSTRAIN` → `MODEL_VARIANT` + `RESOURCE_SUBSTITUTION`". FR-3: "A 70B VLM requiring 48 GB requested by an actor cleared to 24 GB returns `DENY` with `primary_rule_id = R-TIER-02` in 100% of cases; the response names the compliant variants available."
- **Attack:** The §6.2 example ("48 GB requested, actor capped at 24 GB") is a *subset* of row 4's condition ("exceeds the actor's clearance"). Both fire on the same input. §6.2's own mechanism — "The first rule that produces a terminal outcome becomes `primary_rule_id`" with "Precedence is **strict and total**" — means row 3 always wins, so `R-TIER-03` is dead code. FR-3's second clause is therefore unachievable: if a compliant variant exists (the precondition for `R-TIER-03`), the DENY comes from `R-TIER-02`, whose row text specifies no variant enumeration and no next actions; if no variant exists, there is nothing to name. The two clauses "DENY in 100% of cases" and "names the compliant variants available" cannot both hold for the same input. §11 S-2 compounds it: "`R-TIER-02` (primary); `R-TIER-03` when a compliant variant exists" — a prediction the precedence order forbids.
- **Proposed fix:** Move `R-TIER-03` to position 3 and `R-TIER-02` to position 4, and rewrite `R-TIER-02`'s condition as the strict complement: "…and **no** catalog variant satisfies the actor's cap". Then split FR-3's acceptance into two clauses with disjoint inputs: "with a compliant variant → `CONSTRAIN` with `primary_rule_id = R-TIER-03` in 100% of cases; with no compliant variant → `DENY` with `primary_rule_id = R-TIER-02` in 100% of cases."
- **Confidence:** High

### PRD-3 — FR-10's stale-tolerant `ALLOW` directly contradicts NFR-12's fail-closed rule, and the 60-minute schedule staleness destroys the module's headline value

- **Severity:** Critical
- **Location:** FR-10 / NFR-12 / §2.3 item 1 / FR-4
- **Attacked text:** FR-10: "Stale-acceptable per port: enrollment 15 min, schedule 60 min, fleet 60 s, quota 5 s, model catalog 24 h, clock 0 s | `DENY` (fail-closed, `R-DEP-01`) or `ALLOW` on strictly stale-tolerant reads with a `STALE_FACTS` warning", with acceptance "with the model-catalog port down and a cached copy < 24 h old, 100% of requests proceed". NFR-12: "100% of authorization-class rules (`R-FRZ`, `R-TIER`, `R-AUTH`, `R-NIGHT`, `R-LAB`, `R-QUOTA-01`) are fail-closed on indeterminate facts".
- **Attack:** The model-catalog port feeds `R-TIER-01`, `R-TIER-02`, `R-TIER-03` (min VRAM), `R-AUTH-01` (license) and `R-AUTH-02` (weight-class tier) — every one of which NFR-12 classifies as authorization-class and fail-closed. FR-10 says a <24 h-stale catalog yields `ALLOW`; NFR-12 says an indeterminate catalog fact yields `DENY`. There is no reading under which both hold, and NFR-12 has no exception clause. The same collision hits enrollment (15 min → `R-AUTH-01`). Worse, the **schedule** port at 60 minutes is stale-tolerant, and the schedule is the sole input to `R-LAB-01` — so a 60-minute-stale timetable can be blind to a class that started nine minutes ago, and a `TRAINING` request is admitted into a protected window. That falsifies §2.3's value proposition verbatim ("Zero background admissions inside a protected window, provable by replay (FR-4)") and SPEC CAP-2's "zero new non-reserved requests are granted access to hardware inside an active reservation window". A 60-minute staleness budget for a timetable has no upstream basis anywhere in SPEC or the spine; spine rule 2's 60-second freshness bound applies to cluster state, not schedules, and the PRD has silently imported the number.
- **Proposed fix:** Split the staleness table into `fail-closed` (enrollment, quota, clock — 0 s) and `fail-open-with-warning` (fleet, 60 s only). Move schedule and model-catalog to fail-closed, or state explicitly that a stale schedule older than the current protected window's `starts_at` is treated as **no windows present** and therefore **fail-closed**. Amend NFR-12 to: "authorization-class rules fail closed on indeterminate facts; **no authorization-class fact source may be declared stale-tolerant**."
- **Confidence:** High

### PRD-4 — `exam_binding` is an unvalidated, client-supplied M4 reservation id and it is the sole exemption from three rules

- **Severity:** Critical
- **Location:** §5 (`Request`) / §6.2 rows 1, 7, 8, 14 / FR-2 / §3.2
- **Attacked text:** §5: "`exam_binding` (nullable reservation_id)". Row 1: "**and** the request carries no matching `allowances[]` entry". Row 7: "**and** no `exam_binding` matches the window". Row 8: "**and** `no `exam_binding``". FR-2 validation: "allowance must match `exam_binding` **exactly**".
- **Attack:** `exam_binding` arrives in the `Request` — i.e. from the caller. It is a *reservation id owned by M4*, and §3.2's mock/delegate list exposes exactly one schedule port, `GET /schedule/protected-windows`. **There is no port, and no rule, anywhere in this PRD that validates `exam_binding` against M4's reservation records.** A caller that sets `exam_binding` to any string that happens to appear in a `FreezeState.allowances[]` or match a `ProtectedWindow` bypasses `R-FRZ-01` (the emergency exam freeze), `R-LAB-01` (the class protection) and `R-NIGHT-01` (the night window). `R-FRZ-02` then converts that into a positive `CONSTRAIN → WINDOW_SCOPE` admission. The four rules that would validate it are absent, so "match exactly" is exactness against an attacker-controlled string. This is a privilege-escalation-shaped hole in the one module in the platform whose entire job is authorization, and it is invisible to every FR and NFR in the document — NFR-5 scrubs PII from traces but nothing authenticates the requester. Related and same root cause: §5 `Request.actor_ref` is likewise a caller-supplied actor reference, and the PRD has **no authentication step and no identity port at all** (§3.2's first row reads `GET /access/actors/{id}`, and the spine's AD-1/AD-8 path — Gateway auth → Identity Adapter `Resolve(token)` — is simply not represented), so every rule keys off an id the caller chose.
- **Proposed fix:** Add to §3.2 a read-only port `GET /reservations/{id}` owned by M4, add §6.2 row 0: "`R-VALID-01` | `exam_binding` is non-null and cannot be resolved to an active reservation for `actor_ref` within the current protected window | `DENY(INVALID_REQUEST)` | `POL-ENTITLE`", and add an authentication FR: "the actor is resolved from the authenticated session, never from the request body; `actor_ref` in the request is ignored or must equal the session actor." Amend §5 to mark `exam_binding` as "server-resolved, not client-supplied".
- **Confidence:** High

### PRD-5 — The `FreezeState` aggregate has no owner, no read port, and no write interface, yet the PRD owns a freeze console, a freeze state machine, and a 60-second freeze SLA

- **Severity:** Critical
- **Location:** §3.1 (Simulation console) / §3.2 / §9.1 / §2.2 / FR-14 / A-1
- **Attacked text:** §3.1: "**Simulation console** | The developer-facing interactive request evaluator (the standalone prototype), plus the freeze console for Dr. Reed." §9.1: "`ACTIVE` is terminal-with-expiry; `LIFTED` requires a non-empty `lift_reason` and a named operator. A freeze cannot be edited while `ACTIVE`". §2.2: "The ability to activate, scope, and lift a freeze in under 60 s". FR-14: "Console is a client of the same public API — no privileged back door".
- **Attack:** Trace the freeze write path end to end. The "same public API" per §3.1/§7 is: a decision endpoint, `GET /policy/decisions`, `GET /policy/versions`. **None of them writes a freeze.** §3.2's entire mock/delegate list is read-only (`GET …` ×5 plus clock injection), and §3.1's owned surfaces contain no freeze-write endpoint. So Dr. Reed's console has zero write actions; FR-14's "100% of console actions are achievable through documented API calls" is vacuously true of an empty action set, and §2.2's promise — the module's second protagonist's entire reason for existing — has no backend. This is a **spine rule 1 violation by omission**: `FreezeState` is a persistent aggregate with no single writer. Not in §3.1's owned list, not in §3.2's delegate list, not in the spine's component table (which has no freeze-owning component at all — CAP-2's Reservation Coordinator owns *reservation* state, which is not the same thing). Worse, there is no **read** port for freezes either: `DecisionContext` includes `freeze_states[]` but §6.1 step 2's NORMALIZE enumerates only "actor, model, fleet classes" — protected windows, quota facts, and freeze states are never sourced. And §1/§6.1 insist the engine "mutates nothing" and "reads facts", so §9.1's state machine belongs to nobody.
- **Proposed fix:** Either (a) add to §3.1 the owned surfaces "freeze registry: `POST /freezes`, `PATCH /freezes/{id}/lift`, `GET /freezes`" plus the §9.1 state machine, declare M2 the **sole writer** of `FreezeState` per rule 1, and add a `GET /freezes/active` read port to §3.2; or (b) assign `FreezeState` ownership to M4 and remove §9.1, the freeze console, and the A-1 fallback. Option (a) is what the rest of the document already assumes. Add a `freeze_states[]` sourcing line to §6.1 step 2.
- **Confidence:** High

### PRD-6 — NFR-2's "0 outbound network calls per decision" is incompatible with the engine's own eight fact ports and with `DecisionContext` construction

- **Severity:** Critical
- **Location:** NFR-2 / §3.1 / §3.2 / §6.1 step 2 / FR-10
- **Attacked text:** NFR-2: "`0` outbound network calls and `0` model invocations per decision | Static analysis of the engine package + **runtime assertion that the evaluation context has no I/O port bound**". §6.1 step 2: "2. NORMALIZE     resolve actor, model, fleet classes into one DecisionContext with a single fact snapshot". FR-10 trigger: "A fact port returns an error or exceeds `FACT_TIMEOUT_MS = 150`".
- **Attack:** The engine is *defined* as a function of eight remote facts (§3.2: five HTTP GETs, a clock, plus the model's own facts). NORMALIZE cannot construct a `DecisionContext` without invoking them, so the runtime assertion in NFR-2 — "the evaluation context has no I/O port bound" — is a self-refuting spec: satisfy it and `DecisionContext` cannot be instantiated, so every FR fails. Read charitably ("no I/O *inside the pure core*"), the boundary is still unstated, and the measurement method as written does not express it. FR-10 is the harder contradiction: a 150 ms *per-port network timeout* is a network call, and the module's mandatory non-happy path (NP-1, "Quota port down or > 150 ms") is a statement about a network. The reconciliation ("ports are injected interfaces, resolved by the caller; the engine is pure") is nowhere written. Finally, FR-10's validation column says "cached value + its age" and its acceptance says "with the model-catalog port down and a **cached copy** < 24 h old" — but §6.1 says "It holds no cache". **Where the cache lives decides NFR-2**: inside the engine it breaks "no cache", FR-13 and the pure-function claim; outside it, M2 has a second undocumented dependency. The document asserts both positions.
- **Proposed fix:** Restate NFR-2 as: "**0** network calls originating in the `engine/` package; the engine receives a fully-materialised `DecisionContext` and calls no port itself. Ports are invoked by the application shell (`app/`) and a `SnapshotAssembler` is the only component that may do I/O." Change the measurement to: "static analysis that `engine/` imports no `net`, `net/http`, `grpc`, or `os` package, plus a test asserting `evaluate()` can be driven with a fully literal `DecisionContext` and no fixtures directory present." Replace "cached value + its age" with "the last successful snapshot supplied by the caller, with its `captured_at`", and add `captured_at`/`staleness` to §5's `DecisionContext`.
- **Confidence:** High

### PRD-7 — CAP-3 and CAP-7's fourth closed rejection cause ("hardware is currently failing") is missing from the rule set; faults are silently converted into a queue

- **Severity:** Critical
- **Location:** §6.2 row 13 / §3.2 / §5 `NodeClass` / FR-1
- **Attacked text:** §6.2 row 13: "`R-CONTEND-01` | Every class satisfying the requirement has `available_count − cordoned_count ≤ 0` at evaluation time | `CONSTRAIN` → `QUEUE_ONLY` + earliest estimated wait". §3.2: "Fleet inventory, node class availability, cordons, thermal faults | M3 — GPU Lab Digital Twin".
- **Attack:** SPEC CAP-7 fixes a **closed set of four rejection causes**: "requested resource does not exist for this context; requester is not authorized for that resource or context; **resource is currently in a failing state**; requester's quota is exhausted". The PRD's catalogue covers the first, second, and fourth. The third has no rule. §3.2 declares "cordon**s, thermal faults**" as facts the engine reads, and §5's `NodeClass` has a `cordoned_count` field — but `R-CONTEND-01` **subtracts** cordoned nodes instead of denying for them, so a request whose only satisfying class is entirely cordoned/thermally failed is answered `QUEUE_ONLY`. CAP-3 forbids exactly this: hardware that "is currently failing … rejects the request immediately with a **distinguishable** cause", and success requires that outcome be "distinguishable from a queue outcome, in 100% of test cases". The PRD converts a hard rejection into a queue with no distinguishing cause. Note the arithmetic ambiguity too: `available_count − cordoned_count` double-subtracts if `available_count` already means "allocatable", and under-counts if it means "idle" — neither is stated. There is also no `FAILING_NODE` entry anywhere in the `DENY` cause set, so NFR-6's "0 generic denials" and FR-1's closed outcome vocabulary are both violated by omission.
- **Proposed fix:** Add row 0 to §6.2: "`R-FLEET-01` | Every class satisfying the requirement has `failing_count ≥ 1` and `available_count − cordoned_count = 0` | `DENY` | `FLEET-INV-2026-Q3`, `CAP-3`", add `failing_count` to §5's `NodeClass`, and add to the domain model a closed `DENY` cause enum `{INVALID_REQUEST, NO_SUCH_HARDWARE, NOT_AUTHORIZED, HARDWARE_FAILING, QUOTA_EXHAUSTED, WINDOW_PROTECTED, FREEZE_ACTIVE, DEPENDENCY_UNAVAILABLE}` asserted against CAP-7's four. State explicitly whether `available_count` is net of cordons.
- **Confidence:** High

### PRD-8 — `R-QUOTA-02` grants a cap computed from a read balance, which is precisely the read-then-write pattern spine rule 4 calls an invariant violation

- **Severity:** Critical
- **Location:** §6.2 rows 11–12 / FR-8 / NG-3 / §3.2
- **Attacked text:** §6.2 row 12: "`R-QUOTA-02` | `0 < quota_facts.remaining < estimated_need` | `CONSTRAIN` → `QUOTA_CAP`". FR-8: "with `0 < remaining < need`, 100% are `CONSTRAIN` with `QUOTA_CAP` whose cap value equals `remaining`". NG-3: "Meters, decrements, or resets quota | M8 owns balances. The engine reads remaining balance; it never mutates it."
- **Attack:** Spine rule 4: "**Quota/token decrement is atomic, never read-then-write.** Every decrement against a quota-tier balance is a single atomic compare-and-decrement … so concurrent inference streams checked against the same tier can never both pass on a stale balance. … a read-then-write pattern anywhere in the decrement path is an invariant violation, not a future optimization." `R-QUOTA-02` is a read-then-admit: N concurrent requests each read `remaining = R`, each is granted a cap of `R`, and the aggregate grant is up to N×R against a balance that was already near zero. The PRD's NG-3 disclaimer does not discharge the obligation — it *creates* it. Because the module cannot mutate (rule 1/AD-4), the atomic compare-and-decrement must be performed by M8 **at commit time**, and the decision must be explicitly provisional-pending-that-commit. The PRD says the opposite: §9.2 declares `valid_until` to be "The instant after which this decision confers no authority" and §1 calls the output a decision that is journaled and replayable as authoritative. Combine with FR-10's 5-second quota staleness window: a balance may be 5 s old at the moment of grant. SPEC CAP-1's own success signal — "100 concurrent interactive inference requests … zero requests exceeding their tier's balance" — is not achievable on this design. This also makes `R-QUOTA-01` (`remaining ≤ 0` → `DENY`) racy in the other direction: a 5 s-stale zero denies a request that has since been refilled.
- **Proposed fix:** Add a §9.3 "Commit protocol": "a `Decision` carrying `QUOTA_CAP` is **provisional**; the Quota Service's atomic compare-and-decrement at launch time is the binding act, and a failed CAS revokes the grant. `Decision.authority = PROVISIONAL | FINAL`." Add a §6.2 row: "`R-QUOTA-03` | `Decision.authority = PROVISIONAL` and no binding CAS result accompanies the decision | `CONSTRAIN` → `QUOTA_CAP` with `requires_commit_confirmation: true`". Tighten FR-10's quota staleness from 5 s to 0 s (fail-closed), citing rule 4.
- **Confidence:** High

### PRD-11 — `R-STRADDLE-01`'s condition is unsatisfiable as written, so §6.3's mandatory edge case has no working enforcement

- **Severity:** High
- **Location:** §6.2 row 10 / §6.1 step 4 / §6.3
- **Attacked text:** §6.2 row 10: "`R-STRADDLE-01` | **The request would otherwise be `ALLOW`**, **and** `campus_now + expected_duration_min` crosses `ends_at` of any protected window or `starts_at` of any freeze". §6.3: "a job approved under the night policy that runs into a protected morning class window is never silently grandfathered".
